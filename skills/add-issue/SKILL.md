# Add a GitHub issue

Interview the user, draft the issue, confirm it, then create it. Never create the
issue before the user has approved the final draft.

## 1. Pick the repository

1. Call `mcp__github__get_me` to learn the user's login.
2. List candidate repositories with `mcp__claude-code-remote__list_repos`
   (fall back to the repository of the current working directory, from
   `git remote get-url origin`, if that tool is unavailable).
3. Ask with `AskUserQuestion` (header `Repo`): offer up to 4 options — the current
   working-directory repo first marked "(Recommended)", then the most recently
   pushed ones. The user can type any other `owner/name` via "Other".
4. If the chosen repo is not in this session's GitHub scope, call
   `mcp__claude-code-remote__add_repo` with `access: "push"` before writing to it.
   If that is refused, tell the user the reason and stop.

If the user already named the repository (or any other answer below) in their
request, don't ask for it again — use it.

## 2. Ask the questions

Use one `AskUserQuestion` call for the structured choice:

- **Type** (header `Type`): `Bug` — something is broken / behaves wrongly;
  `Feature` — new capability or enhancement. (Other: e.g. chore, docs, question.)
- **Priority** (header `Priority`, optional): `Low`, `Medium`, `High`, `Critical`.

Then ask in plain chat (these are free text; ask them together in one message,
numbered, so the user can answer in one reply):

1. **Description** — what is the issue? For a bug: what happens, where, and the
   steps to reproduce; environment/hardware/firmware version if relevant.
   For a feature: what is missing and who needs it.
2. **Goal** — what should be achieved? For a bug: the expected behaviour.
   For a feature: the outcome / user value.
3. **Definition of done** — the concrete, checkable criteria that mean the issue
   can be closed (tests pass, behaviour X verified on device Y, docs updated…).
4. *(Optional)* Title, labels, assignee, links, logs or screenshots.

If an answer is vague (e.g. definition of done is "it works"), ask one short
follow-up to make it testable. Don't interrogate beyond that.

## 3. Check before drafting

- Look for duplicates: `gh api -X GET search/issues -f q='repo:<owner>/<name> is:issue <keywords>'`
  (or `mcp__github__list_issues`). If a likely duplicate exists, show it and ask
  whether to continue, comment on it instead, or stop.
- Read the repo's `.github/ISSUE_TEMPLATE/` (via `mcp__github__get_file_contents`
  or locally) and, if a template fits the type, follow its headings — filling
  sections from the user's answers and omitting ones that don't apply.
- **Labels — match `/triage`.** Every new issue gets one category label and one
  state label, using the same vocabulary as the `/triage` skill so the issue
  lands in its queue:
  - category: `bug` (Bug) or `enhancement` (Feature / other)
  - state: `needs-triage`
  If `/setup-matt-pocock-skills` has configured a label mapping for this repo
  (see the repo's `CLAUDE.md` / `AGENTS.md` or docs it points to), use the
  mapped label strings instead of the canonical names. Check the labels exist
  with `mcp__github__get_label`; if one is missing, say so in the draft — GitHub
  will create it on issue creation, so the user can choose to keep it or drop it.
  Add any extra labels the user asked for.
- For org repos, check `mcp__github__list_issue_types` and set the issue type if
  `Bug` / `Feature` types exist.
- **Right tool?** If the answers describe several separable pieces of work or a
  whole plan/spec, suggest `/to-tickets` instead (it splits work into
  dependency-linked tickets) and continue only if the user wants a single issue.

## 4. Draft

Title: short, imperative or symptom-based, ≤ 72 chars; prefix with nothing —
the label carries the type.

Body (when no repo template applies):

```markdown
## Summary
<one or two sentences>

## Description
<bug: what happens + steps to reproduce + environment>
<feature: current situation and what is missing>

## Goal
<expected behaviour / desired outcome>

## Definition of Done
- [ ] <criterion 1>
- [ ] <criterion 2>

## Additional context
<links, logs, screenshots — omit section if empty>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Show the full draft (repo, title, labels, body) and ask: create as-is, edit, or
cancel. Apply edits and re-show if changed.

## 5. Create

Load the tool with `ToolSearch` (`select:mcp__github__issue_write`) if needed and
call it with `method: "create"`, `owner`, `repo`, `title`, `body`, and `labels`
/ `assignees` / `type` when set. Report the issue number and URL. If creation
fails (permissions, missing GitHub link), relay the exact reason and give the
user the drafted text so nothing is lost.

After creating, mention that the issue is labelled `needs-triage` and can be
picked up with `/triage` (e.g. "/triage let's look at #<number>").
